# 32 — One-way bookings

**What to build:** A registered user drops the car off somewhere other than where they
collected it. The requirement's own condition applies: the combination is refused unless
the provider has enabled one-way service between exactly those branches.

**Blocked by:** 31, 29

**Owner:** Garfield

**Status:** done — verified against a running app and a real database

- [x] A booking may name a drop-off branch different from its pickup branch
- [x] Omitting the drop-off branch means returning to the pickup branch, which is the
      ordinary case and must stay the simplest one
- [x] A one-way combination the provider has not enabled is refused as a conflict, naming
      the reason
- [x] The direction matters: pickup A to drop-off B is refused when only B to A is enabled
- [x] A drop-off branch belonging to a different provider is refused
- [x] Both branches appear on the booking response
- [x] The drop-off branch is fixed at creation like the rest of a booking's identity
- [x] Every existing booking rule still holds, capacity included

## Notes

- `dropoff_branch_id` is nullable on the `Booking` model (null = round-trip). Added with
  a named FK `fk_bookings_dropoff_branch_id_branches` so the downgrade can drop it by
  name. Autogenerated migration gave it no name; fixed manually.
- Sending `dropoff_branch_id` equal to `pickup_branch_id` is silently treated as null
  (round-trip) rather than an error, since there is nothing wrong with the intent.
- The one-way check uses `db.get(OneWayRoute, (pickup_id, dropoff_id))` — no canonical
  ordering; direction is the key.
- `BookingUpdate` keeps `extra="forbid"` and has no `dropoff_branch_id` field, so
  re-dating cannot change the drop-off branch.
