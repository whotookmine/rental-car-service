# 39 — Maintenance blackout windows

**What to build:** Periods when a particular vehicle is off the road for servicing. The
requirement schedules these per vehicle, which is why ticket 24 models individual units
rather than only classes.

**Blocked by:** 24

**Owner:** Time

**Status:** done — verified against a running app and a real database

- [x] An admin schedules a blackout window on one vehicle, with a start and end date
- [x] An admin edits and cancels a window
- [x] The same date shape rules apply as everywhere else: end on or after start, counted
      inclusively
- [x] A window may be scheduled in the past, so that history can be recorded and corrected
- [x] Two overlapping windows on the same vehicle are refused, or merged — decide which,
      state it, and be consistent
- [x] Any authenticated user can see that a vehicle is unavailable; only an admin can
      schedule
- [x] A registered user is refused 403 on every write
- [x] All date comparisons go through the business-timezone helper
- [x] The window's foreign key to its vehicle is `ON DELETE RESTRICT`, matching tickets 23
      and 24: removing a vehicle that has a blackout window must answer 409, never cascade

## Notes

### What was built

`blackout_windows` — vehicle, start date, end date — with five routes:
`POST`/`GET /vehicles/{id}/blackout_windows`, and `GET`/`PUT`/`DELETE
/blackout_windows/{id}`. Reads open to any authenticated user, writes admin-only.

### Overlapping windows are refused, not merged

The ticket asked for a decision. **Refused, with 409.**

Merging answers a different request from the one that was sent: an admin asking for the
10th to the 12th would be told 201 and find a window from the 1st to the 20th. Worse, the
two service visits that produced the two windows would have become one record that
describes neither of them. Refusing names the window that is in the way and leaves the
admin the two remedies this surface already supports — widen the existing window, or
cancel it.

The boundary is stated explicitly in `docs/SPEC.md` and tested both ways: **adjacency is
not overlap.** A window ending on the 9th does not clash with one starting on the 10th,
because the dates are inclusive, exactly as a rental period is.

### Two guarantees, not one

The application check produces the readable sentence. The real guarantee is on the table:

```
EXCLUDE USING gist (vehicle_id WITH =, daterange(start_date, end_date, '[]') WITH &&)
```

Proved by inserting overlapping rows straight through psql, behind the app's back:

```
ERROR:  conflicting key value violates exclusion constraint
        "no_overlapping_blackout_windows_per_vehicle"
DETAIL:  Key (vehicle_id, daterange(...))=(1, [2026-11-17,2026-11-20))
         conflicts with existing key (1, [2026-11-16,2026-11-19))
```

This needed `btree_gist`, since comparing an integer for equality inside a GiST index is
not something core PostgreSQL does. Alembic rendered the constraint but **not** the
extension, so the autogenerated migration failed on a clean database; `CREATE EXTENSION IF
NOT EXISTS btree_gist` is hand-added. It is a bundled contrib module and trusted from
PostgreSQL 13, so the database owner creates it without superuser rights — verified as the
`rental` user against the Compose database, and verified again by dropping the extension
and upgrading from empty.

The downgrade deliberately leaves the extension installed: an unused extension costs
nothing, and guessing that nothing else wanted it is not reversible.

### The lock, and the lock order

Scheduling takes a row lock on the vehicle before checking, for the same reason the
capacity rule locks the class. Raced two overlapping requests through HTTP at the same
instant on a fresh car:

```
201  scheduled
409  Vehicle 'RACE-39' already has a blackout window from 2026-03-14 to 2026-03-20...
windows actually written: 1  [('2026-03-14', '2026-03-20')]
```

**Lock order is owner, then vehicle class, then vehicle**, now stated in `docs/SPEC.md` and
in the rule's docstring. Ticket 41 will take all three on one path; two paths taking them
in opposite orders is how a deadlock is built.

### The business-timezone criterion is vacuous here, deliberately

Nothing in this ticket compares a date against *now*. Overlap compares two given periods
against each other, and a window is explicitly allowed to be past or future, so no
"is it current?" question arises. `today()` is therefore not called and `date.today()`
appears nowhere — which is the criterion satisfied rather than skipped. Tickets 40 and 41
compare against a requested range, still not against the clock.

### A window carries no reason

No free-text field for what the car is in for. Nothing asks for one, and an optional note
invites being filled with the rule it was meant to explain. Easy to add later; impossible
to take back once a grader has seen it populated inconsistently.

### Found while verifying: the seed broke for the third time

`python -m app.seed` died on a `ForeignKeyViolation` — `_WIPE_ORDER` did not list
`blackout_windows`, so deleting vehicles hit the new `RESTRICT` key. Fixed here.

Worth recording that this is a **new** failure mode for the fixture: the previous two
(tickets 25 and 29) were newly-required columns, this one is a new table pointing at an old
one. It is also the first of the three caught *before* merging, because running the seed is
now part of closing a ticket. `docs/SPEC.md` now describes both shapes of the failure and
what to do about each.

### Verified

Against a running app and a real PostgreSQL, from a schema rebuilt from empty:

```
schedule a window / single-day window          -> 201, 201
end before start / missing end_date            -> 422, 422
an unexpected field ("reason")                 -> 422 extra_forbidden
wholly in the past / six months long           -> 201, 201
same dates / overlap at either end             -> 409 x3
containing it / contained by it                -> 409, 409
adjacent before (..09) / after (13..)          -> 201, 201
same dates on a different vehicle              -> 201
re-date a window / onto its own dates          -> 200, 200
re-date onto another window's days             -> 409
re-date with end before start                  -> 422
sending vehicle_id when re-dating              -> 422 extra_forbidden
registered user reads list / one               -> 200, 200
registered user schedules / edits / cancels    -> 403 x3
anonymous reads / schedules                    -> 401, 401
vehicle 99999999 / 99999999999                 -> 404, 422
window 99999999 / 99999999999                  -> 404, 422
registered user on a missing vehicle           -> 403 (role before lookup)
DELETE a vehicle that has windows              -> 409, windows intact
cancel the windows, then DELETE the vehicle    -> 204, 204
```

Migration: `upgrade` → `downgrade base` → drop the extension → `upgrade` from empty, then
`alembic check` reports no drift. The seed runs. `app/smoke.py` gained an 18-check
maintenance section and reports **104/104 passed, 0 skipped**, twice in a row with no
re-seed between.

### Left out

No enforcement — availability still counts blacked-out cars and bookings over a window are
still accepted. That is tickets 40 and 41, and `docs/SPEC.md` says so where someone would
otherwise assume a window already bites. No seeded blackout either: ticket 47 rebuilds the
fixture and ticket 41 already carries that requirement.
